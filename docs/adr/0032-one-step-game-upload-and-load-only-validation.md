# ADR-0032：游戏包一次上传自动启用与仅加载兼容性验证

状态：Accepted

日期：2026-08-24

取代：ADR-0010 中“上传可替换既有 Game workspace”的公开产品流程

修订：ADR-0008、ADR-0011、ADR-0017 的摄取与兼容性检查边界

## 背景

现有流程要求用户先创建 Game 或选择已有 Game，再上传 ZIP、绑定 workspace、单独验证，最后手动
启用。实际产品没有把新上传包绑定到已有 Game 的需求；每个上传包都代表一个独立游戏。多阶段 UI
和 API 让 staging 预算、状态版本及中间诊断暴露给用户，也放大了“上传成功但无法启用”的失败面。

摄取和启用还在真实 Emuera 初始化之外遍历所有已知文本扩展名，要求编码可由静态扫描器识别，检查
根目录 ERB 结构并搜索禁止能力字符串。这些规则比运行时实际加载的文件集合更宽、更严格，现实游戏
可能因无关文本、未知编码或非典型目录布局被拒绝，即使固定运行时本身能够加载。

## 决定

- 每次上传总是创建一个新的 Game，不再提供把上传包绑定或替换到已有 Game 的产品能力。
- 公开写入流程收敛为一次幂等 `POST /api/v1/games`：请求体是 ZIP，名称和可见性作为请求元数据；
  服务端依次完成有界接收、安全 staging 物化、创建 Game、真实运行时加载验证和 current content
  原子启用，成功时直接返回已可创建 Session 的 Game。
- 不再公开空 Game 创建、`PUT /games/{id}/package`、`:validate` 或 `:activate`。workspace、ingestion
  和 content operation 继续作为内部崩溃恢复边界，不是用户需要推进的资源状态。
- 上传阶段只实施实例容量、归档可读取性和 staging 内安全物化所必需的检查。文件名不再因 Windows
  保留名、尾点/空格、大小写碰撞、Unicode NFC 或内容编码而被拒绝；ZIP 权限和链接类型不落盘，
  所有条目只物化为 API 创建的私有普通文件或目录。绝对路径、父级段、NUL、精确重复和文件/目录
  冲突若无法保持原路径并安全物化，仍作为损坏归档拒绝，不能写出 staging。
- 保留 ADR-0014 的带 BOM UTF-16/UTF-32 到 UTF-8 兼容性转换；转换成功后摘要基于转换后的内容。
  转换失败时保留原始字节，不产生静态编码阻断，最终只由真实运行时加载结果决定能否启用。其它
  编码可以为清单展示而尽力识别，但不得要求所有文件使用特定编码。
- 兼容性验证只在只读 staging 副本中启动固定 `CloudEmuera.Validator`，调用真实 Emuera
  `InitializeAsync`。初始化完成即可启用；初始化返回的运行时错误或 Validator 超时、崩溃、非法
  协议仍阻止启用。目录结构、全树编码、资源引用和禁止能力字符串不再由额外扫描器决定兼容性。
- manifest/digest、文件数/总字节数、只读 current、fsync/原子 rename、持久 operation、授权、
  审计和 SessionRoot 私有复制不变。它们承担容量、一致性和恢复职责，不是内容兼容政策。

## 备选方案

### 保留现有多阶段 API，只简化前端

前端可以串行调用旧端点，但服务端仍允许创建空 Game、绑定已有 Game 和停留在草稿状态，错误恢复、
幂等及公开契约仍围绕用户不可见的中间步骤，因此不采用。

### 保留静态扫描并把错误降为警告

这能减少阻断，但仍会读取所有已知扩展名并产生与真实加载集合无关的噪声。兼容性权威应是固定
运行时能否初始化，因此删除额外内容政策。

### 完全不检查路径并按 ZIP 名称直接写盘

绝对路径和父级段会逃出 staging，NUL 或文件/目录冲突也无法由目标文件系统忠实表达。它们不是
游戏兼容性要求，而是安全物化的技术前置条件，不能取消。

## 后果

- 正常用户只需选择 ZIP、名称和可见性；成功响应中的 Game 已自动激活。
- 新包不再更新已有 Game。需要替换时删除旧 Game（若无 Session 引用）并上传为新的 Game；既有
  SessionRoot 仍保持创建时副本。
- 不相关或静态扫描器不认识的文本编码不会阻止上传；运行时真正读取且无法解码/解析的文件仍会使
  加载测试失败，并返回运行时诊断。
- UTF-16/UTF-32 自动编码转换语义保持不变；旧 Game/current 和既有 Session 不做迁移。
- 安全 ZIP 解析、容量和崩溃恢复代码继续存在，但其拒绝码需区分“归档无法安全物化”与“运行时
  无法加载”，UI 不再把它们统称为路径/编码兼容性检查。

## 验证

- HTTP 集成测试证明一个 ZIP 请求只创建一个 Game，真实加载通过后响应为 current content 已存在，
  可直接创建 Session；相同幂等键不重复创建。
- 旧 ingestion、package、validate 和 activate 公开路由返回 404，上传不能选择已有 Game。
- 包含未知编码的未加载文件、Windows 保留名、大小写不同文件名和非 NFC 名称的包不因静态政策
  被拒绝；容量超限和无法安全物化的穿越路径仍明确失败。
- 真实运行时加载失败、Validator 超时/崩溃/非法协议不激活 Game，并保留可诊断的稳定错误。
- Web 测试覆盖“选择 ZIP + 填写元数据 → 上传中 → 自动启用 → 进入 Game”单一流程。
