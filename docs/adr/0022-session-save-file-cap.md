# ADR-0022：Session 原生存档单文件大小上限

- 状态：已接受
- 日期：2026-08-14
- 关联任务：P1-10

## 背景

P1-10 允许通过 HTTP 流式写入 SessionRoot 中的 Emuera 原生存档。SessionRoot 总容量上限不能直接
作为单个请求的上限：一次超大上传可能在完成校验前消耗过多暂存空间，也可能造成压缩格式检查的
资源风险。需求要求该上限在实现前冻结，不能由实现临时选择一个未记录的常量。

## 选项

1. 每个部署都必须显式配置上限。安全性最明确，但会使没有配置的 MVP 开发环境无法启动。
2. 使用固定的低默认值。容易部署，但限制较小的存档无法上传。
3. 使用一个明确记录的默认值，并允许部署通过 `CloudEmuera:Capacity:MaxSaveFileBytes` 覆盖。

## 决策

采用选项 3。默认 `MaxSaveFileBytes` 为 64 MiB。配置值必须为正数、不超过
`MaxSessionRootBytes`，并在 API 启动时验证。上传在流式计数达到上限时立即失败；声明的
`Content-Length` 超限时在读取请求体前失败。该上限同时约束 `.sav`、`txtN.txt` 和 `imgN.png`。

64 MiB 足以覆盖常见 Emuera 原生存档和辅助截图，同时把单次暂存、格式嗅探和磁盘空间影响限制在
实例容量预算内。该值不是存档格式的一部分，后续调整只通过配置和部署验证完成。

## 后果

- 需要把单文件上限纳入容量配置、OpenAPI 错误映射和上传测试。
- 运行时格式检查仍必须有独立的读取/解压上限，不能因为文件小于 64 MiB 就无界展开 GZip 或 PNG。
- 未来若需要按用户、Game 或格式设置不同上限，应新增 ADR，而不是改变此默认值的含义。

## 验证

- API 以默认值启动，并拒绝非法配置；
- `Content-Length` 和实际流分别覆盖等于上限、超过上限和缺失长度；
- `.sav`、文本和 PNG 在上限内完成基本格式检查；
- 文档、错误码和配置样例引用同一配置键。
